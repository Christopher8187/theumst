# Whole-book upload

A master publishing key submits an archive to `/api/v1/books/ingest-archive`. The proxy applies a route-specific one-GiB request limit. The backend validates the archive and manifest, resolves source identities, writes book/section/knowledge data, manages semantic projections and vectors, and stores image content through the selected adapter. Publisher metadata can overwrite the fields it owns on later uploads.

`services/book_ingestion.py` owns archive processing; `services/knowledge.py` owns lower-level knowledge/embedding submission; `services/graph_sidecar.py` validates and persists optional authored graph data. Read their current schemas and tests before changing accepted fields. Image storage and Qdrant operations do not share PostgreSQL's transaction, so current failures can leave partial external results. Receipt and retry behavior must be verified against the actual chosen path.

Current graph-sidecar storage is book-scoped and validates cycles. Relations of type `dependency` may form cycles: the receipt lists them under `allowed_cycle_components` and the upload proceeds. Edges of all other types, taken together without the dependency edges, must stay acyclic; a cycle among them fails validation, while a cycle that needs a dependency edge does not. The demo's generated order graph is a different representation. [Data architecture](architecture/data.md) records the distinction.

[Settle the full Whole-book upload and integration route](https://github.com/Christopher8187/product/issues/30) owns Kaicenat-produced dependency fields, direction/types, source identities, revisions, empty/missing/invalid data, storage mapping and reader requirements. Its [implementation](https://github.com/Christopher8187/product/issues/66) and [verification](https://github.com/Christopher8187/product/issues/67) follow the earlier Theumst release. Each must read this document, [data architecture](architecture/data.md), [Atlas](atlas.md) and the accepted functional decisions.

Use the [database ingestion tests](../backend/python/tests/README.md) against an explicitly disposable database. A fake cursor can validate query construction, but cannot establish rollback, constraints, external writes or end-to-end publication.

Knowledge objects accept an optional `name`, up to 500 characters. It is the heading beside the working type, such as Bounded sequences beside Context. Existing publishers can omit it. Reimport preserves an existing name when the field is omitted or null; an empty string clears that override. Reader, Atlas and discovery labels use the name when present and otherwise the language-specific label. This field does not rename the whole grimoire. Migration 010 owns its storage.

An object's `source_metadata` may give numeric `difficulty` and `estimated_minutes`. They are stored with the rest of `source_metadata`, and since 0.0.14 the Web Demo's knowledge list and object view return them, or null when either is not a number, as [data architecture](architecture/data.md) explains.

Since 0.0.15 the upload rebuilds its book's whole-book read before it commits, after the graph sidecar, and single-object submission does the same. The receipt's `book_read` gives `{format, version, raw_bytes, gzip_bytes}`, or `{error}` when the build failed. The upload still commits then, and the route answers 409 until a later upload or the [manual run](operations.md#whole-book-reads) builds the book. [Data architecture](architecture/data.md) owns the answer.

Since 0.0.16 the upload and single-object submission also rebuild the book's game row, the answer the game downloads, in the same transaction and a savepoint of its own. The upload rebuilds it again after storing the images, because the answer names them. The receipt's `book_game_read` reports that last build in `book_read`'s shape. Either row can fail alone: its error deletes only that row, and the game's book answers 409 until the next build.

Knowledge objects also accept an optional `crystal_source_key`, up to 255 characters. Objects naming the same key share one knowledge crystal, in this upload and later ones, across books; `is_default_in_crystal` still marks the preferred instance. A reimport moves an object to the crystal its key names. An object without a key keeps its current crystal, or gets a new crystal of its own when it is new. Migration 011 owns the key's storage.

An image entry names the object that shows it in `object_source_key`, and may list every object it belongs to in `object_source_keys`, such as a theorem and the supporting objects that restate its figure. Every key in that list must name an uploaded object. Its `link_type` says how: `figure`, the default, when the objects show the image, or `page` when the image is a scan of a page the objects appeared on. `book_image_knowledge` holds one row per image, object and link type, and a reimport replaces an image's rows. `book_image.knowledge_id` keeps a figure's first object and stays empty for a page scan. The reader's object view and the public API return an object's figures as `images`, including the one an older upload named, and its page scans as `pages`, in page order when the image metadata gives a numeric `page`. The upload reports `image_link_count` and `page_link_count`. Migration 012 owns the links.
