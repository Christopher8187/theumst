# News and subscriptions

News announcements require an explicit choice for the account's current email address. Existing accounts start with no subscription. Profile exposes `GET /api/me/subscriptions` and `PUT /api/me/subscriptions` with `{ "news": true | false }`. The response contains `news`, `status`, `email`, `consent_at`, `consent_source` and `confirmed_at`. Status is `off`, `pending_confirmation`, `active` or `suppressed`. Suppression does not erase the user's recorded choice; an opted-in suppressed address remains visibly suppressed and receives no announcements.

The optional Login checkbox sends `news_opt_in=on`. Consent is recorded only after the password succeeds. A checked choice for an unconfirmed account is pending; login still refuses that account and creates no session. Confirmation activates that same address's pending consent. An absent or unchecked checkbox does not cancel existing consent. Successful email change disables the previous address's subscription and revokes sessions as before; the newly confirmed address requires a fresh explicit choice.

`news_subscription` stores the current choice, email, consent identity, source, time, confirmation and an unguessable unsubscribe token. `news_consent_event` retains opt-in, opt-out and email-change history. The same address's unsubscribe links remain useful after a later opt-in. Changing the address changes the token. Account deletion removes its active subscription; audit events retain the address with no account relation. No subscription rows or historical consent are invented by migration `008_news_subscriptions.sql`.

## Publishing and preview

The existing Media access point authorizes the editor and `POST /api/content/media/email-preview`. Preview accepts `title` and `email_introduction`, and returns `subject`, `html` and `text` without sending or querying an audience. All preview anchors omit their destinations; plain text uses preview placeholders. The introduction is plain text, separately authored from the News body, with a maximum of 5,000 characters. HTML escaping is applied by the renderer.

Media create and update accept `email_introduction` and the default-false `announce`. Announcing requires published status and a nonempty introduction. Publication, the immutable `news_announcement`, its confirmed consenting audience, and `news_delivery` rows commit together. The mutation returns `announcement_queued` and `announcement_id`; Media list also returns `announcement_queued_at`. Each post can queue one announcement. A repeated request returns the existing identity with `announcement_queued: false`; ordinary edits never queue another message. A later subscriber does not join an already queued campaign.

Creating an announced post additionally requires a client-generated `request_id` UUID. The editor preserves the UUID and submitted payload when a response is uncertain and retries that same submission. `media_create_request`, introduced by forward migration 009, stores the editor-scoped UUID, a fingerprint of the normalized payload and the original successful response in the publication transaction. Identical creation retries, including concurrent requests, return that original 201 response without another post or announcement. Different content with an already used UUID returns 409 and directs the editor to refresh and edit the saved post. A failed transaction leaves the UUID available for retry. Existing news-only clients may omit it; new clients should supply it for every creation. PUT edits retain their post identity and do not require a request UUID. Distinct concurrent creations receive distinct slugs. The saved create result remains a historical response even if that unannounced post is later deleted; replay never recreates a deleted post.

The public detail API is `GET /api/news/{slug}`, and emails link to `/news/{slug}`. Drafts are not publicly readable. The slug stays stable when its title changes. Announced posts remain published and cannot be deleted through Media, so delivered links continue to resolve; the editor may correct the post's content. Those invalid delete/unpublish requests return 409 with an explanation.

## Delivery and unsubscribe

`services/news.py` owns the outbox worker. It starts in the backend lifespan only when `NEWS_DELIVERY_ENABLED=true`; the default is false. Multiple workers claim due rows using PostgreSQL row locks and a lease. Before each provider call the worker locks the account and subscription, then checks the confirmed current email, enabled choice, original consent identity, suppression and publication again. A changed choice or address stops the queued delivery. An unsubscribe that completes before dispatch prevents that send. A request arriving after dispatch begins waits for that already-started attempt.

Announcements use Resend's HTTP sending endpoint. The message JSON is persisted once, including both formats and unsubscribe headers. Retries reuse that identical payload and `Idempotency-Key: news/<delivery_id>`. A timeout or lost acknowledgement therefore cannot become a fresh message during the provider's documented 24-hour retention. Retry delays grow to one hour. A row with an unresolved attempt older than 23 hours becomes `uncertain`; the worker never automatically sends it again. Inspect the provider event history or provider logs using its original key before resolving it. Do not reset its time, change its key or blindly requeue it. Permanent provider rejection becomes `failed`; errors store a status/class rather than message bodies or credentials. [Resend idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys) defines the external limit.

The retry-age limit is checked again after eligibility locks and immediately before the provider call. Waiting behind a long account transaction therefore cannot carry an ambiguous retry past the provider's retention window.

Messages include `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. `POST /api/news/unsubscribe/{token}` accepts the mailbox provider's one-click request without login and is idempotent. `GET` shows a confirmation form and never changes consent, including when a mail scanner follows the link. The page uses no external resources, sends no referrer and is not cached.

`POST /api/email/events/resend` verifies the raw body with the endpoint's Svix signing secret, constant-time HMAC comparison and a five-minute timestamp window before interpreting the event. Receipt IDs are deduplicated. Authenticated bounce, complaint and suppression events for the configured sender or a known delivery populate `news_suppression`, even if the event arrives before the sending API acknowledgement. Delivery events cannot overwrite a recorded suppression state. `delivered` means the recipient server accepted the message; it does not establish inbox placement. [Svix verification documentation](https://docs.svix.com/receiving/verifying-payloads/how-manual) describes the signature format.

## Configuration and operation

Set `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `NEWS_DELIVERY_ENABLED` and optionally `NEWS_POLL_SECONDS` (default 10, minimum 2). `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME` and `PUBLIC_WEBPAGE_URL` provide the sender and public links. An empty `RESEND_API_KEY` reuses `SMTP_PASSWORD` only when `SMTP_HOST` is exactly `smtp.resend.com`, because Resend uses its API key for SMTP authentication. Other providers' SMTP passwords are never reused. Account security mail continues through the configured SMTP transport. [Resend SMTP documentation](https://resend.com/docs/send-with-smtp) describes that credential relationship.

Before enabling the production worker, configure the Resend webhook to the selected environment's `/api/email/events/resend` URL for delivered, bounced, complained, suppressed and failed events, install its signing secret, and verify an authenticated test receipt. Enabled startup refuses absent sending credentials or an invalid/missing signing secret. Keep local tests disabled and use injected delivery transports. The release env generator, deployment Compose file and its provisioning example forward these settings without printing their values. Production schema application still requires the reviewed migration runner and a verified backup; see [operations](operations.md).

Operators can inspect counts grouped by `news_delivery.status`, due rows, attempts, `last_error` and provider email IDs using authorized database access. Investigate `failed` and `uncertain` rows and sustained queue growth. A suppression is not cleared automatically by a new opt-in. Removing one requires a deliberate provider/account investigation outside the public subscription API. Stored recipient payloads and unsubscribe tokens are private operational data and must not appear in logs or public API responses.

The September 2026 Outlook sample was in Junk despite passing SPF, DKIM, DMARC and composite authentication; it had Date and Message-ID headers. Its Outlook spam classification was SCL 5. That observation supports checking sender reputation and controlled inbox delivery after changes; it does not justify speculative authentication DNS changes. The shared templates and announcement consent cannot guarantee inbox placement. [Account recovery](account-recovery.md) owns security-email behavior, and [backend tests](../backend/python/tests/README.md) lists deterministic and real database coverage.
