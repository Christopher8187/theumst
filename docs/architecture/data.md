# Data architecture

PostgreSQL is authoritative for users, roles/access, sessions, keys, books, sections, knowledge objects, language-specific content, crystals, semantic projection metadata and study state. Qdrant stores vectors addressed by embedding identity. Storage adapters hold image bytes, with `book_image` connecting them to books and objects. Migration 012 adds `book_image_knowledge`, which links an image to several objects with a `link_type`: `figure` when an object shows the image, `page` when the image scans a page the object appeared on. `book_image.knowledge_id` keeps a figure's first object.

News uses `media_post` for the published story and immutable `news_announcement`/`news_delivery` rows for an explicitly selected announcement and its consenting audience. `news_subscription` binds a choice to one account email, `news_consent_event` records consent changes, and `news_provider_event`/`news_suppression` persist verified delivery feedback. Migration 008 creates no subscriber data. [News subscriptions](../news-subscriptions.md) owns the state transitions, duplicate prevention and unsubscribe behavior.

Migration 009 adds `media_create_request`, keyed by editor and client request UUID. Its payload fingerprint and original response share the publication transaction, preventing a creation retry from becoming a second post and announcement. Rows are removed with their editor account; a post deletion does not permit its old create request to run again.

Migration 013 serves UMST's accounts. `api_rate.requests_per_minute` replaces `searches_per_hour`. `api_rate_window` keeps one live one-minute counter per key and kind (`book` or `character`), and `api_usage_daily` counts accepted requests per key, UTC day and kind. `api_key.client` is `umst` for keys the game's sign-in makes. A `"character"` belongs to a user and has exactly one `character_data` row. It has a `name` of 1 to 50 characters (not unique), `sex`, a `summary` object of at most 2 KiB, `created_at`, `last_played_at` and a lease (`lease_api_key_id`, `lease_expires_at`). `character_data` holds the save as a `jsonb` object of at most 64 KiB, its `save_version` and a `revision` that each save raises. The foreign key from `"character".character_data_id` cascades only from a deleted save to its character. Migration 014 adds the other direction. Its `AFTER DELETE` row trigger `character_delete_character_data` deletes the `character_data` row that a deleted `"character"` row pointed at, whether the game deleted the character or an account's deletion cascaded to it. 014 also removes saves no character points at. Migration 015 adds `lease_install_id`, the game install that took the lease when its call named one in `X-Install-Id`. It holds 1 to 64 letters, digits, hyphens or underscores, is null otherwise, and means nothing without `lease_api_key_id`. `sign_in_attempt` keeps a day of game sign-ins and website logins, each naming either the account's `user_id` or, when no account matches, the SHA-256 of the username as the lookup normalises it. A successful password reset adds a right password for its account with no address, which clears the account's count and no address's. [Game accounts](../game-accounts.md) owns the behaviour.

Books use `grimoire_id`, sections use `section_id`, and source-specific knowledge uses `knowledge_id`. Source keys identify publisher data for updates. A book version is its published edition/version. Crystal membership uses `knowledge_crystal_id`; the preferred instance is marked by `is_default_in_crystal`. Migration 011 adds a nullable, unique `knowledge_crystal.source_key`, so Whole-book upload can place objects that name the same `crystal_source_key` in one crystal. Crystallization reads membership directly and filters hidden sources.

Migration 010 adds nullable `knowledge.name` for an object's heading beside its type. The Demo uses this when nonblank and falls back to `language_knowledge.label`. Single-object submission and Whole-book upload accept an optional name of up to 500 characters. Older uploads that omit it preserve an existing name. It is independent of grimoire titles and crystal names.

`user_grimoire` holds a user's summoned books. `demo_knowledge_progress` has one completion row per user/object. `demo_study_state` preserves independent Text and Questions positions. Hiding a book changes reader visibility without deleting these rows. `demo_note` permits multiple attached notes and separate scribbles. Hidden source labels and links are withheld while the user's writing remains readable. Deletion is different and follows existing foreign-key actions.

The complete compact reader list orders active objects by demo override, canonical source-order metadata, then ID. The gold path uses that complete list. Text navigation skips exercise objects; Questions navigation visits only exercises. Neither skips completed objects. The local display may omit positions but never changes the underlying order.

Since 0.0.14 each row of that list, `GET /api/demo/grimoires/{grimoire_id}/knowledge`, and the `knowledge` object of `GET /api/demo/grimoires/{grimoire_id}/knowledge/{knowledge_id}` carry `difficulty` and `estimated_minutes`. Each is the object's `knowledge.source_metadata` value of that name when it is a JSON number, passed on as stored, and null otherwise: when the key is missing or holds JSON null, text, a boolean, an object or an array, or when `source_metadata` is not an object. The query tests the stored value with `jsonb_typeof` and casts nothing, so none of those values makes the read fail. A number too large for Python's JSON would: an integer of more than 4,300 digits, or a number with a fraction or exponent beyond a float's range, makes both routes answer 500 for the whole book, as it already would in `source_order`. Whole-book upload, the only writer of an object's `source_metadata`, cannot store such a number, so only a direct SQL write could. The two fields follow `completed`; every other field and the row order are unchanged. The Web Demo does not show them.

Migration 016 adds `book_read`, one row per book with `format`, `version`, `body_gzip`, `raw_bytes`, `object_count` and `built_at`. It holds the answer the [whole-book read](../web-demo.md#whole-book-read) serves, built by `services/book_read.py`. The answer is a JSON object of format 1 with `format`, `version`, `grimoire_id`, `graph_capability`, `counts` and four lists:

- `sections`: every section of the book as `{id, parent_id, number, name, depth, minutes_own, minutes_whole}`, in a depth-first walk of the contents tree. Roots and children sort by `section_number` as text, then id. Orphan sections and their children follow at depth 0. `name` is the language-1 section name or null. The minutes are `section.source_metadata.minutes.own` and `.whole` when they are JSON numbers, otherwise null.
- `objects`: the rows of the complete reader list above, in its order, as `{id, section_id, type, name, label, source_key, difficulty, estimated_minutes, crystal_id, crystal_default, role}`. The reader's `completed` is left out. `role` is the graph sidecar's role or null.
- `relations`: for each relation type in `knowledge_graph_edge`, the `[source, target]` pairs whose two ends are in `objects`, sorted by source then target. In `dependency` the target uses the source. In `supports` the source supports the target.
- `crystals`: each crystal holding two or more of the book's objects, as `{id, members}` with members in book order. Members in other books are left out, so another book's upload never changes this answer.

Statements and workings stay on the one-object route. The version is the SHA-256 of the answer without `version`, serialized with sorted keys, compact separators and UTF-8. The body adds `version`, and `body_gzip` is that body at gzip level 9 with mtime 0, so the same facts always give the same bytes.

Whole-book upload and single-object submission rebuild the book's row before they commit, under `pg_advisory_xact_lock(hashtext('theumst.book_read'), grimoire_id)`. The upload builds after the graph sidecar, or after the objects when there is none. The build runs in a savepoint. If it fails, the row is deleted and the upload still commits, so the route answers 409 instead of serving facts that no longer hold. An unchanged version writes nothing, and deleting a book deletes its row. Hiding a book, title and ISBN edits, images, embeddings and readers' state change nothing in the answer. Any other change to a book's facts, such as direct SQL, a restore or a release that raises the format, needs the [manual run](../operations.md#whole-book-reads).

Two authored relation stores currently exist: legacy `relation` allows one type per ordered object pair and can cross books; graph-sidecar tables allow typed book-scoped edges and multiple types. The sidecar validator rejects directed cycles, except among `dependency` relations, whose cycles it lists in the receipt. The demo graph endpoint's default view generates `book_order_v1` with `authored_dependencies: false` in its projection metadata; it does not establish authored dependencies.

The Atlas requests `/api/demo/grimoires/{id}/graph?focus={id}&view=atlas`. This view reads only explicit `dependency` edges from `knowledge_graph_edge`, with both endpoints active in the selected demo-visible book. It does not reinterpret other relation types or legacy cross-book edges. It returns adjacent reader positions within 24 steps and an undirected dependency walk of up to eight steps, covering both slider ranges. Transfers stop at 150 nodes and 600 edges; truncation is reported. The browser applies its smaller display limits. Books without dependency data retain reader-order navigation. Reader positions use the same demo override, canonical metadata and ID fallback as the complete compact list. Object imports carry that metadata in `source_metadata`.

The Atlas repair consumes the explicit dependency type already supplied by the demo sample; it does not settle those remaining integration decisions.
