# Backend tests

Run `python -m pytest tests` from `backend/python` after installing `requirements-dev.txt`. Use LOCAL configuration and isolated service addresses. On Windows put Git for Windows `bin` before System32 in PATH so shell checks use Git Bash rather than the WSL launcher.

The endpoint and service unit tests use scripted cursors or HTTP transports. They check authentication order, data filtering, error behavior, ingestion validation, account/token handling and deployment guards without establishing database persistence. `test_similar_retrieval.py` covers the retained single-book endpoint and crystallization; `test_discovery.py` covers the current cross-book discovery service. `test_reviewed_migrations.py` checks pinned sources and refusal of partial state.

`test_api_key_auth.py` checks the per-minute windows per kind, Retry-After, the refusal of master keys before counting, the access-point refusal before counting that master keys pass, and daily usage. `test_book_access.py` drives `/api/v1` through the application with a stand-in that answers each query by its text. Each book read refuses a key of an account the Web Demo does not admit with 403 `demo_access_required` and counts nothing. It serves a key of an admitted account and every master key. Book images also take a session with Demo access and answer 401 without a key or session. The test lists every `/api/v1` route as a read or a master-only write, so a new route fails it until someone classifies it. `test_game_api.py` drives `/api/game` through FastAPI: sign-in with its account lookup, advisory locks, per-account and per-address limits and the replacement of the computer's earlier key; the key re-check inside each character transaction; the character list, leases, revisions, size limits, deletion and the error shapes. It also checks `X-Install-Id`: its validation before the key, two installs under one key, a lapsed lease, calls without the header, and that no game call asks for an access point. `test_default_api_key.py` covers the Default key on the API Keys page, the confirmation that makes no key, and the revocation of game keys; `test_password_recovery.py` checks that a reset revokes them and clears the account's wrong-password count in its own transaction, and that an unknown, used, unsent or expired link changes nothing. `test_game_accounts_schema.py` compares migration 013 with `schema.sql` as text, including the readiness markers. `test_login_limit.py` drives `/auth/login` through the same limiter: its answers kept from before, the decoy check for unknown usernames, 429 with `retry_after` and `Retry-After`, the form post's redirect, and the same statements as the game's sign-in for the same attempt. `test_character_data_deletion_schema.py` checks that migration 014 and `schema.sql` make the same function and trigger, and checks 014's cleanup of saves without a character, its pin and its readiness markers. `test_character_lease_install_schema.py` does the same for migration 015's column and check, which match the header's pattern. These use scripted cursors. No module runs migrations 013 or 014 in PostgreSQL; their first real run is the release check on a restored copy of COM, with the queries in [game accounts](../../../docs/game-accounts.md#checking-migration-013) and [for 014](../../../docs/game-accounts.md#checking-migration-014). Migration 015 runs in `test_key_access_postgres.py` below, on a table shaped as 0.0.12 left it; its release check uses the queries [for 015](../../../docs/game-accounts.md#checking-migration-015).

`test_sign_in_postgres.py` requires `THEUMST_SIGN_IN_DB_TESTS=1`, LOCAL loopback settings and a PostgreSQL account that may create a temporary database. It creates a UUID-named database from `schema.sql`, removes it afterward, and never changes the configured source database. Through `/auth/login`, `/api/game/sign-in` and `/auth/reset-password` it checks with PostgreSQL's own counts and transactions that ten wrong passwords lock an account at both, that a reset lets its owner sign in at once with the new password, that an address past thirty wrong passwords still waits after the reset, and that a refused link, or a reset that fails after clearing the count, clears nothing. Its default skip must be reported separately.

`test_key_access_postgres.py` requires `THEUMST_KEY_ACCESS_DB_TESTS=1` and the same settings, and makes and removes its own UUID-named databases. Through the application it checks book reads against PostgreSQL's own access map. An ordinary account's key reads no book and counts nothing. Keys of betatester, manager, admin and superadmin accounts read and count, and a master key of an ordinary account keeps its access. Approving an account's Web Demo request opens its keys' reads. A book image follows the Demo's own auth-check for a session, and the game stays open to an account outside the Demo. Two installs under one key go through open, heartbeat, save, delete, the list, close and a lapsed lease, beside calls without the header. A second database starts with `"character"` as 0.0.12 left it and a live lease on it. Startup readiness refuses it, the reviewed runner applies only 015, the column and its check then match a fresh schema's, and the file runs twice more without change. Its default skip must be reported separately.

`test_book_ingestion_database.py` requires `THEUMST_DATABASE_INTEGRATION=1`. It inserts real books, nested sections, objects and projection metadata in PostgreSQL, checks returned identities, then rolls back. It does not send vectors to Qdrant. Its default skip must be reported separately. Conftest import fallbacks are for unit tests; a real-service run must have actual psycopg2 and password hashing dependencies installed.

`test_atlas_graph_database.py` uses the same disposable-database opt-in and rollback. It checks the demo route against stored dependency edges, undirected traversal, inactive endpoints, unrelated relation types, bounds and missing relations. `test_real_analysis_sample.py` builds the sample manifest with Node and checks the object metadata consumed by ingestion.

`test_news_email.py` checks escaped shared templates, actual expiry settings, explicit publication validation, Resend retry identity and Svix's published verification vector with tampering/replay rejection. `test_news_postgres.py` requires `THEUMST_NEWS_DB_TESTS=1`, LOCAL loopback settings, disabled news delivery and a PostgreSQL account that may create a temporary database. It creates a UUID-named database from `schema.sql`, removes it afterward, and never changes the configured source database. Real HTTP/SQL checks cover pending login consent without a session, personal subscription access, immutable audience/payload, publication deduplication, durable slugs, safe GET and idempotent POST unsubscribe, email-change consent isolation, retries and their cutoff, concurrent workers, suppression and early provider events. Every provider transport is injected or forbidden. The default skip must be reported separately.

The same database suite covers creation request replay after a lost response, changed-content conflicts, editor scoping, concurrent identical requests, retry after transaction rollback, optional legacy news-only requests and concurrent distinct slug allocation. These checks exercise real unique constraints, advisory locks and transaction boundaries without sending any email.

A controlled-clock test holds an actual account row lock while a delivery waits, advances beyond the retry limit, and verifies that dispatch stops as `uncertain` after the lock releases. This checks the time limit at dispatch as well as at initial claim.

Release acceptance also exercises the current endpoints against PostgreSQL and Qdrant, independent realm positions, hidden-source note persistence, and real schema upgrade/fresh initialization. The [browser objectives](../../../docs/testing/web-demo.md) describe observable flows; [testing](../../../docs/testing.md) owns evidence requirements. Keep temporary users, vectors and databases separate from production.
